# Current Work

## Active

### Validator classes (schema-aware lifecycle)
Validators are still factory functions instantiated once at init time. They now use **time-of-use** access for schema prerequisites (variables, rulesets) — lookups happen inline when needed, not hoisted to factory scope. Guard patterns vary by validator file (optional chaining, nullish coalescing, early returns).

The longer-term fix is converting validators to proper classes with lifecycle management (subscribe to `schemachange` events, refresh cached prerequisites).

### Deferred styling work
- Move PixiLayerRapid's hardcoded styles into the style asset file (colors are currently dynamic from `dataset.color`)
- Have PixiLayerRapid call `styleMatch()` with a dataset/scope ID
- Per-dataset schema querying (different presets for Rapid vs OSM data)

### Performer-inspired statistics display
- HUD overlay showing frame timing (APP/DRAW split), scene complexity, draw calls, texture usage, queue depth
- Data sources: `scheduler.metrics`, GraphicsSystem performance marks (already in place, commented out), Pixi renderer stats, `scheduler.numPending`
- Inspiration: SGI Performer's `pfStats`/`pfFrameStats` system (Chapter 23 of Performer Programmer's Guide)

## Recently Completed (one-liners)
- **Worker companion convention + MapWithAI conversion** (Mar 2026) — Established `*.worker.ts` companion file convention. Companion files export named listeners that are registered in two places: (1) worker via `index.worker.ts` barrel, (2) main thread via `worker.registerListener()` at service init. NetworkSystem's `_dispatchFetch` routes named tasks (`task` + `taskData` in `NetworkFetchOptions`) to WorkerSystem when available, or calls the registered listener directly as fallback. Services use a single `network.fetch()` call — no dual paths, no local `inflight` tracking. `MapWithAIService` is the first conversion: `'mapwithai:fetchAndParse'` runs fetch + XML parse in either context, returning `ParserResult`.
- **WorkerSystem extraction** (Jun 2026) — Extracted worker pool + listener registry from SchedulerSystem and NetworkSystem into dedicated `WorkerSystem`. SchedulerSystem focuses on scheduling (game loop, queues, timers, backpressure). WorkerSystem owns: worker pool (lazy spawn, round-robin, workerURL, maxWorkers), listener registry (`registerListener`/`unregisterListener`/`getListener`), worker lifecycle (`terminateWorkers`, resetAsync cleanup). NetworkSystem changed optional dependency from `'scheduler'` to `'worker'`. HTML entry points set `worker.workerURL`. MapWithAIService registers listeners on WorkerSystem. 146 tests passing across both SchedulerSystem and WorkerSystem test files.
- **NetworkSystem service migration — COMPLETE** (Mar 2026) — All services migrated to use NetworkSystem. OsmService was the last major one: removed 3 redundant inflight caches + dead `seen` Set, added `hasMatching()` to NetworkSystem, fixed copy-paste bug in note POST handlers, renamed `osm-note-` → `osm-note-tile-` to avoid prefix collision. VectorTileService's PMTiles path intentionally bypasses NetworkSystem (PMTiles owns its fetch). NetworkSystem at 100% coverage (32 tests), OsmService 40 tests pass.
