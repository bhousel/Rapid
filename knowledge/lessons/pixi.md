# Lessons: Pixi rendering

How Pixi behaves, and what that means for Rapid.

- **Mark features dirty when styles change** — `immediateRedraw()` alone doesn't work. Call `gfx.scene.dirtyScene()` before redraw so features re-fetch their style.
- **Pixi v8 `textureSpace: 'local'` stretches the texture to fit each stroked shape's bounding box** — read `node_modules/pixi.js/lib/scene/graphics/shared/utils/generateTextureFillMatrix.mjs` for the exact math. In the `'local'` branch, Pixi computes `bounds = shape.getBounds()` of the current stroke instruction and maps UV so (0,0) = top-left of bounds, (1,1) = bottom-right. The user-supplied `style.matrix` is then composed on top. A dash texture stroked one segment at a time (as `DashLine` did, before it was replaced by `LineMesh`) stretches one full cycle across each segment with `'local'` — longer segments = bigger dashes. Use `textureSpace: 'global'` for tiled patterns where the cycle length must be independent of segment length. (`'global'` is misnamed: it does NOT use worldTransform; it just normalizes UV by `texture.source.width/height` per pixel.)
- **Rapid supports the WebGL1 renderer path** — e.g. `?renderer=webgl1` in the URL. WebGL1 only supports REPEAT wrap on power-of-two textures, so a texture that repeats (a dash pattern from `PixiTextures.getDashTexture()`) is a power of 2 wide, with the pattern stretched over all of it: its texture coordinates count in repeats of the pattern, not in texels, so the width doesn't show.
- **Pre-multiplied matrices: scale BEFORE rotate** — with uniform scale, scale-then-rotate and rotate-then-scale produce the same matrix. With non-uniform scale the order matters. In Pixi's pre-multiply convention (`scale()`, `rotate()`, `translate()` all pre-multiply), do `m.identity(); m.scale(sx, sy); m.rotate(angle); m.translate(tx, ty)` — result is `M = T * R * S`, so a vector is first scaled (in the texture's own axes), then rotated, then translated. Reverse order tilts the texture's axes.
- **A halo's `scale` vs container scale are independent axes** — `drawHalo()`'s `scale` says how many of the container's units a screen pixel is (it multiplies the halo's width and dashes). Container scale controls the Pixi transform hierarchy. For Line/Polygon features (`container.scale = 1`, drawing in world units), pass `localScale` (`2^(WORLD_ZOOM-zoom)`). For Point features (`container.scale = 1/worldScale`, drawing in CSS pixels), pass `1`. Don't conflate the two.
- **`viewZoom` vs `styleZoom`: always use the right zoom for each purpose** — `viewZoom = viewport.transform.zoom` is the true Mercator zoom; use it for scale chain math (`worldScale = 2^(viewZoom - WORLD_ZOOM)`). `styleZoom = map?.effectiveZoom() ?? viewZoom` is latitude-adjusted; use it only for LOD thresholds and visual style decisions (e.g. `styleZoom < 16`). Mixing them causes features to scale incorrectly at high latitudes. Name them explicitly in functions that need both.
- **Don't accept "works for one caller" as a fix for a shared utility** — If a `useTexture: true`/`false` toggle changes visible output for the same input, that's a bug in the utility, not a configuration choice for callers. Look at the math before reaching for a workaround.
- **Pixi v8 renderer is NOT re-entrant** — never call `renderer.render()` or `renderer.generateTexture()` inside a layer's render path. The renderer shares batcher / renderPipes / renderTarget state across the whole frame; a nested render corrupts whichever slots are in flight. Symptom: intermittent visual glitches (garbled textures, smeared/wrong-UV meshes) on the FIRST frame an object enters the scene, which self-heal on the next clean render. Label texture creation is now deferred through `SchedulerSystem.schedule()` so it runs after frame callbacks. Remaining known risk: `PixiFeaturePolygon` still uses `PIXI.GpuGraphicsContext` + `buildContextBatches` to extract geometry; replace that with direct tessellation.
- **`gl.readPixels` is a GPU pipeline flush** — every `renderer.texture.getPixels()` call forces the GPU to finish all queued work, then blocks the CPU on a synchronous readback. N readPixels in one frame = N full pipeline stalls. Avoid per-frame; if you need pixel data, batch it or move it off the render-tick critical path.
- **`createImageBitmap` only helps if you don't read it back** — `fetch` + `createImageBitmap` moves PNG/JPEG decode off the main thread, but `drawImage(bitmap)` + `getImageData()` immediately turns it back into a main-thread copy. Prefer direct DOM-source atlas uploads (`texSubImage2D(..., source)` / `copyExternalImageToTexture`) or, for tile seams, one extra canvas draw that stays out of JS pixel arrays.
- **Tile seam padding is not an atlas-wide requirement** — Opaque map tiles need edge-replicated padding to avoid dark seams under bilinear sampling. Symbols, text, and icons can usually leave the reserved 1px ring transparent; copying their edge pixels just adds work and can make antialiased transparent edges worse.
- **ImageBitmap lifetime matters with direct atlas uploads** — If the atlas stores an `ImageBitmap` directly, closing it before upload invalidates the source. It is safe for background tiles to close immediately after `PixiTextures.allocate()` only because tile sources are copied into an edge-padded canvas before returning. Non-tile bitmap callers must keep the bitmap alive until upload/free or hand the atlas a canvas instead.
- **`PIXI.CanvasTextMetrics.measureText(str, style)` measures without rasterizing** — pure CPU canvas-2D `measureText`, internally cached, returns `{ width, height, ... }`. Prefer this when you only need glyph dimensions for placement; don't pay for a `new PIXI.Text()` + `generateTexture()` + `readPixels` round-trip just to read `getLocalBounds().width`. Texture frame size adds padding: `frame = ceil(measured + style._getFinalPadding() * 2)`.
- **`BatchableMesh.uvs` returns RAW geometry UVs when `textureMatrix.isSimple === true`** — `isSimple` is true when the texture frame matches its source dimensions, rotate is 0, and no trim. Atlas textures (where the frame is a small sub-rect of a 2048² source) are reliably NOT simple, so this isn't a bug for the labels/symbols/tiles atlases. But it's a footgun for full-source textures (e.g. a one-off pattern that happens to be exactly source size): a `MeshRope`/`MeshPlane` built with a geometry that assumes atlas UVs will skip the UV-remap and draw garbage. If you find a mesh drawing the right glyph at the wrong UVs, check whether the texture frame == source dimensions.
- **A Pixi render group stores its vertices as 32-bit floats relative to the group** — so a group's children must have small coordinates. Ours are in z16 world coordinates, and `isRenderGroup` on `origin` drew circles as ovals in Bochum at z18 (a float32 is exact to 1 world unit there, 4 screen pixels). The timings looked great and showed nothing wrong: look at a screenshot too, somewhere far east and zoomed in. `PixiScene.worldContainer()` puts each render group at an anchor near the view (`design/scene.md` section 3).
- **Drawing a feature costs little in the APP pass and a lot in DRAW** — `feature.update()` took 2 to 3 µs, so a frame with 19 ms of APP budget drew 7,000 new features, and Pixi then spent 212 ms building their geometry in the DRAW pass. A budget on APP time alone doesn't bound a frame: count what the work will cost in DRAW too (`RenderFrame.drawDebt`).
- **Many small frames can cost more than one big one** — each frame pays for a DRAW pass, and in a dense place Pixi's DRAW costs 50 ms whatever changed. Spreading Užice's restyle over frames of 6 ms of work took 44 frames and 2.2 s; with each frame's budget as long as the last DRAW pass, 12 frames and 1.0 s.
- **A render group is rebuilt whole, and replayed every frame** — Pixi collects everything in a group again when one thing in it is added, removed, shown, hidden or (for a `Graphics`) redrawn: 35 ms for one line among Užice's 18,882. Draw calls aren't a one-time cost, but they're cheap (about 3,400 replayed in 6 ms there); each group adds a few microseconds a frame. So split big groups by something that keeps the draw order (lines: road class, then tile), and measure both sides: the changed frame and the frame that only moves the view.
- **Moving many children between Pixi containers: empty the old one whole** — moving features to other tile containers one by one made Pixi rebuild both containers on every frame it happened (40 to 100 ms of DRAW, for 30 frames). Moving them all in one frame was 250 ms. `removeChildren()` on a whole old container, a few containers a frame, costs each new container one or two rebuilds and no frame more than 20 ms.
- **Removing a Pixi object isn't freeing it** — `removeChildren()` and a new `mesh.geometry` left the old objects to Pixi's own collector, which frees what's been unused for a minute. Under use that was 550 MB alive that nothing showed. A heap that falls by itself after a minute of idling is this.
- **When containers get a new level, find who walks them** — splitting the points into a container per map tile put a level between `points/osm` and the features. `PixiLayerLabels.gatherAvoids()` walked that container's children as features, so it made one avoid box per tile and none per pin: labels over pins in some places, no labels at all in others. No test looked at labels against points. Code that reads another layer's containers should find features by what marks them (`container.__feature__`), not by depth.
- **An option a library doesn't know is silently ignored** — `events: { globalMove: false, … }` sat in the Pixi options from 2023, with a comment in `AGENTS.md` saying those events were off. Pixi reads `eventFeatures`. Check the running object (`renderer.events.features`), not the options you passed, and put the check in a test.
- **`WORLD_ZOOM = 16` is load-bearing, not stylistic** — Pixi's CPU-side geometry builders (`buildLine`, polygon triangulator) silently skip segments below an internal pixel threshold. At z0 storage, typical features (a ~20m building ≈ 3e-5 world units) fall under that threshold and disappear from hit areas / generated geometry. Pre-scaling world coords to z16 keeps geometry in a range Pixi's primitives accept. The pre-scale looks redundant given that we re-scale per-frame at every layer, but reverting it breaks `helpers.lineToPoly()` and anything else that feeds raw world coords into a Pixi geometry primitive. Don't try to remove it again. Symptom: tiny/missing hit areas, missing custom-built geometry, no console errors.
- **An upstream "fixed" may not be our bug: run our own reproduction before removing a workaround.**
  Rapid#1636 (a partial fill's mask crashing in `MeshPipe`) had a workaround that replaced the mask.
  It was removed in May 2026 because pixijs#11207 was closed as fixed. That fix was for missing uvs,
  which only our playground had; the playground never reproduced the real cause (a mesh crossing
  100 vertices in a frame where its render group rebuilds), and the crash came back in Nov 2026
  (pixijs#12437). Before dropping a workaround, check the fixed version against what crashed in Rapid.
- **A bug that needs "the same frame" has to be forced, not waited for.** The mask crash needed a
  mask to cross Pixi's batching line in a frame where something else changed its tile, then a later
  frame that moved the tile without a rebuild. It reproduced in a few lines by doing those steps
  with a render after each (headless Chromium, `node_modules/pixi.js/dist/pixi.min.js`). In Rapid it
  also needed a mask that Pixi had never batched: one batched once keeps a stale place in an old
  batch and is written there instead of throwing (the e2e test, which is about a `LineMesh` now
  that the masks are gone, calls `mesh.unload()` first).
