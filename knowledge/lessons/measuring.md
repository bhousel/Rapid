# Lessons: Measuring performance

How to measure frames, memory and garbage without fooling yourself. See also "Measuring" in
`design/graphics-system.md`, and the measurements themselves in `design/graphics-system-log.md`.

- **Measure a frame the way it happens for the user** — `bun run measure` used to call `immediateRedraw()` after each pan step, which (a) says "something changed", so no layer could keep its features, and (b) runs the passes back to back. A real drag makes no redraw request and its APP phases came 250 ms apart (the throttle before frame pacing), where the same pass costs about twice as much (21.6 ms against 11 in Seattle, nothing moving). Drive real pointer events at least once before trusting a scripted number: a real drag over a new area also showed the Rapid datasets' tiles asking for a redraw of everything. And start a scripted drag where nothing is under the pointer, or it drags a node.
- **Compare two builds in one session** — `bun run measure` on the same build, hours apart, gave Seattle's redraw frame as 10.8 and 17.5 ms and Staten Island's cull frames as 63 and 100 ms. To see what a change did: measure, stash the change, build, measure, pop, build, measure again (one place is enough, with `--runs 15`).
- **Time the parts before designing around the whole** — a zoom's restyle took 139 ms in Seattle, and the plan was to spread it over frames. Timing its parts first showed 85 ms of it was `styles.styleMatch()` and the `style` setter, for styles that don't depend on the zoom: the layer's loops said `if (feature.dirty)`, and a zoom makes everything dirty. Not doing that work (`feature.needsStyle`) cut the restyle to a third before any of it was spread out. Wrap the suspects with timers in the page (`bun run cdp eval`) before building machinery.
- **Say what "loaded" means before explaining why it takes long** — `bun run measure`'s load time at Staten Island was 32 s, and I wrote that loading waits on the network. Watching the requests showed the 20 tiles had arrived after 2.6 s and everything was drawn after 8: the other 24 s were the script waiting for the scheduler's queues to empty. One request log would have shown it.
- **Feature filters don't mean the same across versions** — with `disable_features=landuse`, Rapid 2.5 and iD hide most areas (their landuse rule is "an area that isn't a building, water, …"), and Rapid 3 hides only what its `filter_landuse` ruleset names. Staten Island showed 6,500 features in Rapid 2.5 and 16,000 in Rapid 3 for the same view. To compare editors, hide only boundaries.
- **Check what the debug Chrome hides before comparing two runs** — its feature filters, area fill and layers are stored in the profile, and every script that doesn't set its own gets them. One day's heap and zoom numbers for Užice were taken with landuse hidden (a filter left on earlier), and the next day's without: 102,510 features against 106,801, which read as the new build allocating 10% more. A script that measures should say what it loaded (features made, features visible) beside its numbers, and two builds should be measured in one sitting. `bun run measure` sets its filters itself and prints them.
- **Measuring can use up the OSM API's patience: record the place** — about forty reloads of dense places in a day, and later five loads of Užice in an hour and a half, and the API answered 429 to every map request. Use a tape (`--tape`, `scripts/tape.ts`): one download, then every run is answered from the file. It's also the only fair comparison: two live runs of the same build gave Užice's first pan as 14 and 16 frames a second, and from the tape it was 18 both times, the same as the build it had seemed slower than.
- **Check that the plan's grouping matches the data before building it** — points were going to be split by rows of tiles, which keeps their north-to-south order exactly. A count in the loaded scene showed 12,870 of Užice's 49,259 points in one row, and that a pan sideways touches every row. Ten minutes with `layer.features` settled it.
- **Before comparing two builds' screenshots, compare two loads of one build** — the split's screenshots differed from the old build's in up to 39,000 pixels. So did two loads of the same build: tile containers and equal lines were drawn in the order they were made, which depends on timing since features are made over frames. Ordering them by tile and ID made the picture repeatable (4 to 660 pixels), and then a diff means something.
- **Before making an expensive thing cheaper, count who asks for it** — the OSM pass takes 207 ms in Užice, and the plan was to speed it up. Logging who called `immediateRedraw()` while the pointer moved showed one caller, 198 times: the hover. Drawing a hover without a pass took a pointer move from 184 ms to 12, with the pass exactly as slow as before.
- **Work done without the pass has to be checked against the pass** — drawing a hover, an edit or a change of mode by redrawing only what it affects is right only if a full pass afterwards changes nothing. That's cheap to check (describe what's shown, run a pass, compare) and it found a real difference at once: "what's related to the selection" goes by links that are made when a way is drawn, so the changed ways have to be drawn before the vertices are sorted out.
- **When passes stop, find what was counting them** — the OSM layer destroyed a feature it hadn't seen for 20 passes, and the pass was also where empty tile containers were removed and where the layer learned what the view had moved over. With tiles and box moves drawn without a pass, each of those needed its own trigger (a count of box moves, a note of when a feature was hidden). Before removing a regular event, list what else happened on it.
- **Once the frames are short, the long stalls are somewhere else** — with no passes left in a pan of Užice, the longest gaps were merges of arriving tiles (80 to 134 ms each), which run outside frames and scheduler tasks, so no frame statistic shows them. Log gaps between ticks next to the frame stats.
- **When the same action is slow once and fast the next time, trace garbage collection before the code** — a selection that took 218 ms took 8 the next time, and 12 the first time after a reload, so it wasn't the selection or a first-time cost. A CDP trace (`Tracing.start` with `v8` and `devtools.timeline`, `console.timeStamp()` around each action) showed a `MajorGC` ending inside each of the three slowest frames. A CPU profile has no timeline to show it, and its "(garbage collector)" line was 1.5%.
- **A trace's `MajorGC` event is the end of a collection, not all of it** — it was 35 to 50 ms inside frames of 600, which looked like the collection explained a tenth of them. Summing the `V8.GC_…` events on the main thread in the same window (without counting nested ones twice) gave 530 to 650 ms: the whole frame.
- **Ask the heap sampler two questions** — with `includeObjectsCollectedByMajorGC` and `…MinorGC` it says what was allocated (what makes collections come); without them, started before the load, it says what's alive (what makes each one long). Both are cheap enough for a 2 GB heap, where a snapshot isn't.
- **Count who asks before making something lazy** — making a node's `Geometry` lazy saved nothing at first: one call in validation (`graph.extent()` for every entity) built all 243,565. A counter in the getter with a sampled stack found it in one load.
- **A check that makes garbage changes what it measures** — the harness that compares the scene before and after a pass builds a string per feature, 100,000 at a time, and the heap grew by 700 MB or more between major collections while it ran. Its timings include collections that real use wouldn't have as often.
- **Log every frame of the slow case before tuning the rule** — Užice's load looked like a budget that was too small. A log of each frame (pass or not, what it made, who asked for it) showed 27 passes that made nothing, asked for by icons loading, and a "scheduler is busy" signal that the frames themselves kept on. Neither was in the budget rule.
- **A signal you read may be one you cause** — the frame's budget was small "while the scheduler has tasks", and the tasks were queued by listeners to the frame's own `draw` event, and never ran because the frames were long. Check who fills a queue before treating its length as someone else's need.
- **Work after a pause runs at half speed** — on the M4, the same OSM pass took 27 ms straight after another and 54 ms after 250 ms of an idle page (35 ms after only 50). With the main thread kept busy through the gap it stayed at 27, so it's the processor slowing an idle thread down, not the JIT, caches or GC. A benchmark that waits between samples measures the slow case, and a real drag (pointer events all the time) the fast one. Say which one a number is.
- **Alternate the variants, and read the noise where the change can't matter.** Comparing mask
  batch modes, one run of each looked like a regression at Staten Island, where 3 of 25 masks were
  affected: noise (0.3 to 0.7 ms of DRAW). Two rounds of A B C A B C with `--runs 15` showed only
  Seattle moving (261 of 300 masks affected), by about 1 ms, every time. Count what the change
  touches at each place (a snippet over the scene) before reading a difference.
- **Two runs of `bun run measure` may not have had the same layers on.** The debug Chrome keeps
  what was last set (layers, filters, area fill), and the script measures with that. Step 5's
  table was taken with the labels layer off, and the next step's first run with it on: 20 more
  draw calls and a few ms of APP that had nothing to do with the change. The first lines of the
  output say which layers and filters were on: read them before comparing. Better, compare in
  one build, alternating: `--setup snippet.js` runs in the page before each place, to switch
  what's compared (`layer.useBatches = false; layer.reset();`) and to set what's shown.
- **A checksum of a typed array has to leave out its huge values.** A sum over a batch's floats
  included a "never" of 3e38 in most vertices, and nothing else that changed could move it: the
  test passed whatever happened to the array.
- **A wait that hits its timeout has found something.** A script waited for `gfx.pending` to be
  false and ran to its 90 s timeout in some states. That was noted as a quirk of the script
  and worked around for a day. It was Rapid drawing sixty frames a second for good after a pan
  with the labels layer off. When "idle" never comes, ask the app who's waiting (each layer's
  `numWaiting`) before lengthening the timeout.
- **Label placement isn't the same on every load.** Two loads of one build and place differed
  in 9,000 pixels in Seattle, all labels: placement follows the order features are drawn in,
  which follows the frames' timing. Compare screenshots with the labels off, or compare two
  ways of drawing in one load.
- **GPU time from two sessions can't be compared.** Staten Island's frame read 7.8 and 8.0 ms
  one hour, 5.8 to 6.2 the next (four runs), and 6.6 and 7.7 after that, drawing the same
  562,000 triangles. Within a session, alternating, the readings held: four ways of drawing
  small areas kept their order in both rounds. A difference between this turn's table and the
  last one's is not a result; measure both sides again, in one run of the script.
- **Check an estimate against a count before it's written down.** "A small building is about 45
  triangles" came from dividing a difference by a guess at how many there were. A snippet that
  walked the batch said 17, and that most were parking spaces, not buildings.
