# Known Quirks

Runtime issues, workarounds, and things that will bite you if you don't know about them.

- **Asset loading vs. render loop timing** — `loadStyleAssetsAsync()` / `loadSchemaAssetsAsync()` at runtime: Pixi keeps rendering during async loading. Current hack: `gfx.pause()` / `gfx.resume()` / `gfx.scene.reset()`. Needs a proper solution.
- **FilterSystem.getMatches** — Skips vertices entirely (returns empty Set). Skips relations unless `tags.type === 'boundary'`. Multipolygon relations get `'area'` geometry, not `'relation'`.
- **RapidSystem._datasetsChanged** — Color-assignment logic is acknowledged as "weird" in code comments. Legacy behavior from before Rapid#1642.
- **ImagerySystem builtins** — `'none'` and `'custom'` sources always exist regardless of merged assets.
- **Structured clone kills DOM objects in workers** — `utilFetchResponse` parses XML into xmldom `Document` objects. These can't survive `postMessage` (structured clone strips prototype methods like `getAttribute`). Services returning XML must either: (a) use `mainThread: true` on `network.fetch`, or (b) parse in the worker and return plain `ParserResult`. `NetworkSystem.worker.ts` provides `fetchAndParseOsmXml` and `fetchAndParseOsmJson` listeners that use approach (b) — parsing happens in the worker, returning structured `ParserResult`.
- **osm-auth mock store vs globalThis.localStorage** — In environments without `localStorage` (unit tests without happy-dom), osm-auth keeps its tokens in an internal Map. `authenticated()` returns `true` after preauth. Read the token with `oauth.getAccessToken()`, which works with either store.
- **Canvas renderer limitations** — `renderer=canvas` URL param enables Pixi's experimental canvas renderer (v8.16+). Known issues: no Mesh support, and since lines and the outlines of areas are meshes (`LineMesh`, Nov 22) the map is blank: Pixi doesn't skip a mesh there, the first frame that updates one throws (`validateRenderable` of `undefined`), and every frame after it. Left as it is (Bryan, Nov 22, when it was reported as lines missing): the option was an experiment, nobody relies on it, and mesh support is Pixi's to add. Also: pattern fills may not work from atlas-packed textures. Atlas textures (symbols, text, tiles) work via canvas-backed `AtlasTextureSource`. `PixiTextures.createTexture()` uses `renderer.generateTexture()` + `renderer.texture.getPixels()` → the canvas path should work since `getPixels` goes through `CanvasTextureSystem.getPixels()`, but test thoroughly.
- **Microtask avalanche from worker results** — Promise `.then()` chains triggered by worker `onmessage` → `pending.resolve()` run as microtasks. The browser event loop MUST drain the entire microtask queue before the next macrotask (including `requestAnimationFrame`). When multiple tiles resolve in the same frame, the entity construction + graph rebase work (~11ms per tile) cascades without yielding. `resultPriority` on `WorkerSystem.dispatch()` mitigates this by routing resolution through SchedulerSystem's frame-budget-aware drain loop. Without `resultPriority`, any new worker listener that triggers heavy main-thread work will hit the same issue.
- **Stale Bun transpiler cache → `describe is not defined`** — Bun 1.4 caches transpiled files by content hash in `~/Library/Caches/bun/@t@/` and doesn't record whether a file was compiled *as a test* (with the injected `describe`/`it` import). If something loads a test file as plain JS once, `bun test` reuses that entry and fails at line 1:1 with `ReferenceError: describe is not defined`. That happened to `test/dom/operations/extract.test.js` (then `test/browser`) in Oct 2026. Confirm with `BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 bun run test:dom`. Fix by deleting the bad `.pile` entry, or `rm -rf ~/Library/Caches/bun/@t@`. Don't edit the test to "fix" it.
- **'strict-dynamic' blocks static imports in a module worker started from a blob** — Rapid's CSP (`scripts/content_security_policy.ts`) has `'strict-dynamic'`, which ignores the `'self'` and host allowlists. A module worker from a `blob:` URL that does `import "https://…"` (or even a same-origin URL) fails with a bare `error` event and no CSP report on the page; `import()` inside the same worker works. MapLibre v6 starts its worker that way when loaded cross-origin, so `Map3dSystem` fetches `maplibre-gl-worker.mjs` itself and passes a blob of its code to `setWorkerUrl()`.
- **Pixi's `MeshPipe` and a mesh that crosses 100 vertices** — In `'auto'` batch mode, a `Mesh` given a geometry on the other side of 100 vertices in a frame where its render group rebuilds throws `Cannot read properties of null (reading 'updateElement')` on later frames, or stops following its parent (pixijs#12437, open). Workaround: a fixed `geometry.batchMode` (every `LineMesh` uses `'batch'`; the partial fill masks it was found with are gone). Remove it once Pixi has a fix, after running the e2e test against that version ("keeps drawing a line whose mesh crosses 100 vertices…").
- **With the labels layer off, `gfx.pending` stayed true after a pan** (Nov 23): fixed the same day. The labels layer counted the scene's notes about labels as placement that was waiting, and took none of them while it was off, so it asked for a frame after every frame (`PixiLayerLabels.render()` throws them away now). A script that waits on `gfx.pending` should still have a timeout, and say when it hit it.
